# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

CZL Browser is a Windows desktop application for managing isolated browser instances with per-instance proxy binding. Built with **Wails v2** (Go backend + React/TypeScript frontend embedded in a WebView2 window), it compiles to a single `czl-browser.exe`.

Key capabilities: multi-profile browser management, proxy pool (HTTP / HTTPS / SOCKS5 entered by users; subscription-imported Clash nodes still run through the Xray / sing-box bridges), Chrome fingerprint spoofing, quick launch (Ctrl+K), backup/restore, OAuth2 login via CZL Connect, paid end-to-end-encrypted cloud sync with teams (see "Cloud Sync, Teams & Billing").

Workspaces, teams, entitlements and billing are CZL Connect application services (orgs / app billing / data sync), not a separate backend. `docs/` is gitignored except `docs/design/`; the local-only `docs/commercialization/` "Browser Control Plane" plan is superseded by Connect and must not be implemented.

## Repository Layout & Commands

The repo follows the CZL layout: everything for the app lives in `desktop/` (one Go module `github.com/woodchen-ink/czlbrowser/desktop`, package `main` at its root plus `internal/` and `cmd/updatesign`), and build tooling lives in `scripts/`. The code base was fully rewritten in 2026-11 and git history was reset at that point.

```powershell
pwsh scripts/dev.ps1                       # wails dev (Vite on 127.0.0.1:5218, bindings at http://localhost:34115)
pwsh scripts/build.ps1                     # desktop/build/bin/czl-browser.exe, version "dev"
pwsh scripts/build.ps1 -Installer -Version 2026.11.22.1 [-WithKernel]   # + dist/CZLBrowser-Setup-<Version>.exe (NSIS)

cd desktop
go test ./...                              # all Go tests
go test ./internal/proxy -run TestGolden   # single test
cd frontend; npm run build                 # tsc + vite build -> frontend/dist
```

`scripts/installer.nsi`, `close-processes.ps1`, `build.ps1` and `dev.ps1` must stay UTF-8 **with BOM**: Windows PowerShell 5 and NSIS misread Chinese text otherwise. `scripts/config.init.yaml` is the default config the installer writes. Dev mode keeps all data under `desktop/` (`desktop/config.yaml`, `desktop/data/`, `desktop/chrome/`); `desktop/config.yaml` is tracked but local edits to it must never be committed. `wails dev` watches the whole `desktop/` tree including `data/`, so starting an instance can make the dev page reconnect and can block renames inside profile dirs; that is a dev-only artifact.

### CI (GitHub Actions)

`.github/workflows/build.yml` builds the Windows installer on every push to `main` (doc-only changes ignored) and on `workflow_dispatch`. It runs `scripts/build.ps1 -Installer` (wails build → stage `dist/stage` → NSIS). The installer **omits the chrome kernel** (gitignored, unavailable in CI); `installer.nsi` makes the `SecChrome` section conditional via `!if /FileExists`, so the same script packages with-kernel locally and without-kernel in CI. Each run uploads the installer as a 90-day artifact and publishes a GitHub Release tagged `v<YYYY.MM.DD>.<run_number>` (date computed in UTC+8 so it matches local; run number disambiguates same-day builds). Each build is a new historical Release, but `make_latest: true` keeps the newest one as GitHub's "Latest" so consumers get a stable pointer to the newest build. The asset is named `CZLBrowser-Setup-<fullVersion>.exe` (version in filename); CZL Connect resolves assets by alias glob on the latest release, so a version-stamped filename is fine. Windows-only by design — proxy runtime, NSIS and WebView2 are Windows-specific.

Before binding generation, `build.yml` refreshes the embedded fallback `desktop/builtin_cores.json` from the remote manifest (see below). It validates the result with `TestBuiltinCoresManifest` and keeps the repo copy if the fetch or validation fails.

**App update publishing** (end of `build.yml`): `wails build` injects the version with `-ldflags "-X main.AppVersion=<fullVersion>"`. Local builds stay `dev` and never report an update. Users get everything through CZL Connect's release download (slug `czlbrowser`), which proxies this repo's Releases and is reachable from mainland China. Alias `windows` maps to the installer (`connect.czl.net/dl/czlbrowser/<tag|latest>/windows`) and alias `update-manifest` maps to the `latest.json` asset. Connect's own `/dl/czlbrowser/latest.json` is an unsigned release summary, and the client does not use it. Before the Release step the job writes `manifest.json` (`version/platform/publishedAt/changelog/fileName/size/sha256/downloadUrls`, URL = Connect fixed-tag `windows` link) and signs it with `go run ./cmd/updatesign sign` into an Ed25519 envelope `{manifest: base64(raw bytes), signature}`. It re-verifies the envelope with the client's embedded public key (`TestReleaseEnvelope`) and uploads it as `latest.json` next to the installer. Secret: `UPDATE_SIGNING_KEY` (base64 32-byte seed from `go run ./cmd/updatesign keygen`). The build fails without it. The public `woodchen-ink/czlbrowser-releases` repo is retired, and CI no longer writes to it. Clients ≤ 2026.09.17.14 still read its `main/latest.json` and get pointed at 2026.10.31.15. That installer kills itself during online update, so those users need one manual reinstall. OpenList (`drive.czl.net`) is not used because its GitHub Releases driver cannot proxy private-repo assets. `downloadUrls` is a list, so mirrors can be added without touching the client. The www landing page (`czl-browser/BrowserClient.tsx`) links to `connect.czl.net/dl/czlbrowser/latest/windows`.

**Kernel list pipeline** (lives in the public `woodchen-ink/Chrome-exe`; czlbrowser is private, so users can't download its release assets). `sync-chrome-stable.yml` runs daily at UTC 01:00 and has two jobs:
- `sync` queries Google's Omaha update server (`POST tools.google.com/service/update2`, Chrome appid, `ap=x64-stable-multi-chrome`) for version/URLs/sha256/size (it used `Bush2021/chrome_installer`'s `data.json` until that account vanished in 2026-09), downloads the official offline installer from Google domains only, verifies Google's SHA256 and size, extracts `Chrome-bin/` with 7z, and publishes `Chrome-bin.zip` + `.sha256` as a Release tagged with the version. 7z quirks: newer 7-Zip extracts `Chrome-bin/` directly while older p7zip needs a second pass on `chrome.7z`; exit code 1 is only a warning.
- `manifest` (`if: always()`) updates the repo's `cores.json`, which the client fetches at runtime, then commits and purges jsDelivr. The entries update independently: one failing upstream still lets the others update, and the job fails at the end.
  - `chrome-stable` = this repo's newest `Chrome-bin.zip` release (tag = version).
  - `clearcote` = the newest non-draft release of `clearcotelabs/clearcote-browser` that has `clearcote-<ver>-windows-x64.zip`. Upstream `releases/latest` is the SDK (`sdk-v*`) and every browser build is a pre-release, so never use `latest`.

Every entry requires an `<asset>.sha256`. Regexes use `[.]` instead of `\.` so they survive shell escaping on every platform. The whole pipeline was verified end to end with a real run: `cores.json` was seeded with the stale clearcote pre.21, and the job moved it to pre.22.

## Architecture

### Wails Binding Pattern

`App` (`desktop/app.go`, package `main`) is bound to the frontend; every exported method becomes `window.go.main.App.*` with generated bindings in `desktop/frontend/src/wailsjs/` (regenerate with `wails generate module`, never edit). `main.go` resolves the layout (dev vs installed), creates `App` and wires the Wails lifecycle and tray. The backend pushes events with `a.emit` (e.g. `proxy:speed:result`, `proxy:iphealth:result`, `browser:instance:started|stopped|crashed`, `backup:export:progress`, `download:progress`, `app:request-close`); `started`/`stopped` carry the profile id string, `crashed` an object.

### Data Flow

- **Install root & layout** (critical, follows the CZL desktop install rule): the installer does a per-user install into the fixed root `%LOCALAPPDATA%\CZL\CZL Browser` (`config.InstallRoot()`). It uses `RequestExecutionLevel user`, has no directory page, writes the uninstall key to HKCU and never triggers UAC. That root holds `czl-browser.exe`, `bin/`, `config/config.yaml`, `data/`, `chrome/` and `logs/`. Roaming `%APPDATA%` is never used. If `LOCALAPPDATA` is missing, startup exits with an error and there is no fallback to the cwd or exe dir. Upgrades replace only program files. The installer writes its default config only when neither the new config nor a legacy one exists. Uninstall always removes the exe, `bin/` and shortcuts, and asks before deleting `config/data/chrome/logs` (the default keeps them). **Legacy layout migration**: older builds installed into `C:\Program Files\CZL Browser` (HKLM key) with config at `%APPDATA%\CZL Browser\config.yaml` and data at `%LOCALAPPDATA%\CZL Browser`. The installer's `.onInit` detects the HKLM key and offers to run the old uninstaller through `ExecShellWait` so UAC can elevate it. On production startup, `config.MigrateLegacyLayout` renames legacy entries into the new root before loading config. Directories are merged entry by entry, existing target files are never overwritten, failures are logged and don't block startup, and emptied legacy dirs are removed. Stored paths are relative to `dataRoot`, so they survive the move.
- **Paths & data root**: `appRoot` = exe directory (dev: project root) — bundled resources only (`bin/xray.exe`, `bin/sing-box.exe`). `dataRoot` = writable data root: dev = project root, production = the install root. `configPath`: dev = `<project>/config.yaml`, production = `<install root>/config/config.yaml` (`config.ConfigPathIn`). `main.go` resolves both and injects them via `App.SetLayout(dev, dataRoot, configPath)`. All writable data — `data/` (db, snapshots, auth, user-data), `chrome/` kernels, logs, proxy workdirs (`data/_xray`, `data/_singbox`) — resolves under `dataRoot` via `App.resolveAppPath` / `browser.Manager.ResolveRelativePath`. `config.yaml` reads/writes go through `App.mainConfigPath()` / `browser.Manager.configSavePath()` (→ `configPath`, falling back to `dataRoot/config.yaml` when unset, e.g. tests), never via `resolveAppPath`. Never put `--user-data-dir` under `C:\Program Files`: Chromium's mojo IPC and network sandbox fail with `拒绝访问 (0x5)` there, and the process exits before its debug port opens. `killResidualRuntimeProcesses(appRoot, dataRoot)` scans both roots (bin under appRoot, chrome under dataRoot).
- **Database**: SQLite (`data/app.db` under `dataRoot`) via DAO pattern. Auto-migrated on startup.
- **Config**: `config.yaml` at `configPath` (production `<install root>\config\config.yaml`). Loaded with auto-repair on missing fields. Supports runtime reload via `ReloadConfig()`.
- **Proxy runtime**: `bin/xray.exe` and `bin/sing-box.exe` shipped in-repo, resolved under `appRoot` (exe dir). No external downloads needed.
- **Chrome kernels**: Placed in `chrome/` directory under `dataRoot`, either user-provided or downloaded from the built-in list. Managed through the UI's core management page. The built-in list is fetched at runtime by `app_builtin_cores_manifest.go`: raw.githubusercontent.com and jsDelivr copies of `Chrome-exe/main/cores.json` are requested concurrently with a 6s timeout and the system proxy, and the first valid response wins. A good result is cached to `data/builtin_cores_cache.json` and reused in memory for 10 minutes; `BrowserBuiltinCoresRefresh` forces a refresh. On failure it falls back to that cache, then to the embedded `desktop/builtin_cores.json`. Entry fields: `id/name/version/kind/release/description/downloadUrl/sha256`. `parseBuiltinCoreManifest` drops any entry whose download URL isn't `https://github.com/…`, whose sha256 isn't 64 hex characters, or whose id is a duplicate. When `sha256` is non-empty, `DownloadAndExtractCore` verifies the zip before extracting it. Don't rename the ids `clearcote` / `chrome-stable`, because the pipeline keys on them. The core management page loads this list without blocking the local core table.
- **Switching an instance's kernel**: verified on one profile, going Chrome 153 → Clearcote 149 → 153 → 149. Cookies (including HttpOnly), localStorage and sessions survived each step, and no downgrade snapshot or wipe happened. That works because portable kernels encrypt with DPAPI only (`os_crypt.encrypted_key`, no `app_bound_encrypted_key`), and all 28 real local instances were checked to be the same. The kind is re-detected at every launch, so args always match the current kernel. What does change is the fingerprint seen by sites (brand/GPU/canvas implementation), and large version downgrades can hit DB schema incompatibilities. `BrowserEditPage` warns in both cases, when the kind differs or the target major version is lower. `GetChromeVersion` also reads the `<version>/` dir name for the official `Chrome-bin` layout, which has no root `.manifest`.
- **Kernel kinds & launch strategy**: `browser.DetectCoreKind(chromeExe)` looks for Clearcote's own switch string `canvas-bridge-url` inside `chrome.dll` (at the kernel root for Clearcote, under `<version>/` for official Chrome) and caches the result in memory keyed by dll path + mtime + size. No DB column is involved, so manually added and backup-imported kernels are covered too. `buildKernelLaunchPlan` then branches on the kind. **chrome** (official Google Chrome, which ignores every `--fingerprint-*`/`--timezone` switch; the `TZ` env var was verified to have no effect as well): keep the short-format `--fingerprint-webgl-*` args and inject stealth + timezone over CDP after launch. **clearcote** (engine-level fingerprinting, BSD-3, verified on 149): no CDP injection at all. Args are translated: `--fingerprint-webgl-vendor/renderer` → `--fingerprint-gpu-vendor/renderer` in the full ANGLE format real Chrome reports (Clearcote returns values verbatim, and short strings are a detection tell), `--fingerprint-touch-points` → `--fingerprint-max-touch-points`, platform `mac` → `macos`, and the effective timezone is passed as the native `--timezone`, which reaches every renderer so pages, cross-site iframes, workers and popups all agree (the upstream PATCHES.md mentions `--clearcote-timezone`, but that name is stale and has no effect). Without `--fingerprint-brand` Clearcote reports the Chromium brand.
- **Window close**: `app.close_action` in config (`tray` default incl. empty, `quit`, `ask`; `app_close.go`). `beforeClose` hides to tray, quits (stopping instances like the tray 退出), or emits `app:request-close` for `CloseConfirmModal`; while a backup import/export holds `maintenanceMu` it always asks. The modal's 记住我的选择 and 设置 → 通用 → 关闭窗口时 both call `SetCloseAction`.
- **Snapshots**: `data/snapshots/<profile id>/<snapshot id>.zip` + `.meta.json`. File names never include the user-given name: a `:` in it becomes an NTFS alternate data stream and the file vanishes from listings. Older `<id>_<name>.*` files are still found by id prefix.
- **Singleton cleanup**: before launching an instance, `cleanupChromeSingletonLocks` removes stale `SingletonLock`/`SingletonCookie`/`SingletonSocket` from the profile dir — these point at the old host after a cross-machine backup import and otherwise make Chromium exit immediately. Runs alongside `patchChromePreferencesForCleanStart`.
- **Backup export/import**: Full backup (`BackupExportPackage`/`BackupImportPackage`) packages config, SQLite, proxies and browser user-data into a ZIP. Two exclusions keep the package small and config-focused: (1) Inside each Chromium profile only real account data is kept; everything rebuildable is dropped. Profile roots are detected structurally via `backup.DetectProfileRoots` (a dir directly containing `Default/` or `Local State` is a profile root — works for UUID and user-named `UserDataDir` alike, not by name matching). `backup.NewProfileAwareSkip` then whitelists `Default`/`Profile N`/`System Profile` data dirs plus key top-level files (`Local State` etc.), dropping component-updater dirs (`WasmTtsEngine`/`WidevineCdm`/`OnDeviceHeadSuggestModel`/…), telemetry (`BrowserMetrics`/`DeferredBrowserMetrics`), in-`Default` rebuildable caches (`Cache`/`Code Cache`/`GPUCache`/`Service Worker` cache, and `Download Service` background-download staging, often tens of MB in a fresh profile), and blocked extension bodies under `Extensions/` for Adobe Acrobat (`efaidnbmnnnibpcajpcglclefindmkaj`), Google Docs Offline (`ghbmnnjooekpmoecnnnilnnbdlolhkhi`), IDM Integration Module (`ngpampappnmepgilojfohadhhmbhlaek`), and Chrome Web Store Payments (`nmmhkkegccagdldgiimedpiccmgmieda`). Bitwarden (`nngceckbapebfimnlniiiahkandclblb`) and `Local Extension Settings` are kept. The same blocked extension bodies are removed again before launching a profile so historical imports are self-healed. Non-profile data under `data/` (SQLite, snapshots, auth) is always kept. Applied on both export (per scope entry) and import (`backupImportFileTrees`). This drops a real ~3GB `data/` to ~250MB. (2) Kernel binaries (`chrome/` under `dataRoot` and config-referenced external cores) are not exported — only their path references travel with `config.yaml`/`browser_cores`; the user re-downloads/re-places same-named kernels on a new machine (into `%LOCALAPPDATA%\CZL\CZL Browser\chrome` in production). Import still restores kernels from older packages that contain them. Backup scope is built from `dataRoot` (data/db/logs/chrome) with `config.yaml` sourced separately from `configPath`. Before copying, export runs `PRAGMA wal_checkpoint(TRUNCATE)` so `app.db` holds the latest writes. `DetectProfileRoots` matches `Default` / `Local State` by exact name (`ReadDir`), because the default instance's folder `data/default` would otherwise make `data/` itself look like a profile root on case-insensitive NTFS and drop `app.db` from the backup.
- **Timezone spoofing**: Browser launch strips the stored `--timezone` flag and resolves the effective timezone (proxy exit locale, falling back to the manual value). Clearcote gets it back as a native switch (see above). Standard Chrome gets a timezone override through browser-level CDP auto-attach so existing and newly opened page targets stay aligned with the proxy exit locale (or manual timezone fallback). Every attached session (any target type, injected or not) must get `Runtime.runIfWaitingForDebugger` (`resumeTargetIfWaiting`): popups from `window.open` are paused on attach even with `waitForDebuggerOnStart:false`, and since they share the opener's renderer, skipping the resume leaves the new tab at `about:blank` and freezes the opener under a "已在调试程序中暂停" overlay. `stealthScript` is wrapped in an IIFE because it runs twice per document (`addScriptToEvaluateOnNewDocument` + `Runtime.evaluate`), and top-level `const` redeclaration would throw (surfacing as a `window.open` exception in popups).
- **Auth**: OAuth2 via CZL Connect (`connect.czl.net`). Encrypted token + user info persisted to `data/auth_token.json` (`storedSession` envelope; legacy token-only files auto-migrated). On startup `TryRestoreSession` restores synchronously from disk (no network) so login survives restart and tolerates offline/weak network; `RefreshSessionAsync` then refreshes the token and re-fetches user info in the background, emitting `auth:restored` / `auth:session:expired` to the frontend. A token is only cleared on definitive refresh failure (`invalid_grant`), not on transient userinfo errors. App requires login to use — OAuth2 provides identity only. CZL Connect also sends a `groups` permission array in `userinfo`, but the app is free/open-source and does not tier users: `auth.UserInfo` deliberately omits the field (`encoding/json` drops it), `AuthState` carries no `level`, and no user-level/permission-group UI exists. Re-introducing tiers means re-adding the field plus its parsing — the payload shape has changed before (comma string → array), so parse defensively. Auth state managed by `authStore` (Zustand).
- **App self-update**: `update.FetchLatest` requests every URL in `ManifestURLs` concurrently (8s, system proxy). Today the only URL is Connect's `/dl/czlbrowser/latest/update-manifest`, which has about 60s of cache. It waits for every response and keeps the **highest** version that passes verification, so a mirror added later with a stale copy can't hide a new release. `ParseEnvelope` verifies the signature against `update/pubkey.go` before trusting anything. It also requires `platform=windows-x64`, a `fileName` matching `CZLBrowser-Setup-<digits/dots>.exe` (the name is used as a local path), a size of at most 512MB, a 64-hex sha256 and https URLs. Rotating the key means changing `pubkey.go` and shipping a build signed with the old key first. `UpdateDownload` downloads into `data/_update/` in the background and tries the URLs in order. A 30s stall watchdog moves on to the next URL. The size and sha256 are checked on the stream, and the `.part` file is renamed only when they match. Progress is sent as `update:progress` (`downloading/ready/error`), and older installers are removed. `UpdateInstall` verifies the file again and starts `installer /S /RELAUNCH /WAITPID=<pid>` detached, then calls `ForceQuit`, which stops instances and proxies gracefully. NSIS `.onInit` waits up to 60s for that PID (`Wait-Process`) before its usual process cleanup. `CloseInstalledProcesses` force-kills every process whose exe is under the install root, so it must pass `-ExcludePath "$EXEPATH"`, because the update installer itself runs from `data/_update`. Without that it kills itself and the update silently does nothing. Helper processes go through `nsExec` (no console window), and `SetCompressor` sits at the top of the script because any plugin call before it breaks compilation. and `.onInstSuccess` relaunches the app when `/RELAUNCH` is present. In silent mode MessageBoxes use `/SD` defaults. Frontend: `AuthenticatedApp` runs `useAppUpdate` (check at login, then every 6h, one notification per version), `store/updateStore.ts` holds the state, the Sidebar shows a dot on 系统设置 when an update exists, and `modules/settings/sections/UpdateGroup.tsx` is the 软件更新 group under 设置 → 通用 (check, download, confirm install and restart).
- **Cloud sync, teams & billing**: see the section below.
- **Profile quota**: Instance create/copy flows are not blocked by `MaxProfileLimit`; there is no quota / redeem / license UI (the old 个人信息 page and keygen page are gone; `app_license.go` is unused by the UI).
- **Instance kernel = follow default**: an empty `coreId` means "follow the global default kernel" and is resolved only at launch (`ResolveChromeBinary`). Create and `ApplyDefaults` must never write the current default id into the profile, or switching the default stops affecting it. A `coreId` that doesn't exist on this machine (e.g. chosen on another computer in a synced space) also falls back to the default, and `CountInstancesByCore` counts it there. Migrations v8 / v10 reset ids equal to the default or dangling in `local`.
- **Groups & tags (unified)**: instances have one group (`browser_groups`, single level; `ParentId` is always forced to `""`, migration v9 flattened old trees) plus tags; proxies have one group (`group_name`) plus tags; cores and bookmarks have tags only. Tags are JSON string arrays on each row (`tags` column; proxies also carry them in `ProxyWire`, bookmarks inside the synced JSON) and are normalized by `browser.NormalizeTags` (trim, case-insensitive dedupe). `app_taxonomy.go` renames / deletes a tag or proxy group across all rows of one kind; 设置 → 分组与标签 drives it. List pages share `components/taxonomy` (group pills for quick switching, multi-select tag filter that matches any). Instance keywords still exist in the data model and sync wire but have no UI.
- **Default proxy for new instances**: `browser.default_proxy` stores a proxy-pool id (resolved in the current space by `resolveDefaultProxy`; ignored if that space lacks it). Values containing `://` are legacy raw proxy URLs and are used as a custom proxy.
- **Last start time**: `browser_profiles.last_start_at` is a local-only column written by `MarkStarted` on launch (not synced, no dirty mark, no `updated_at` bump); the list's 上次启动 and the dashboard's activity read it.

## Cloud Sync, Teams & Billing

Reference implementation is CZL TradeDocs (`czlexpress-tradedocs/desktop/internal/cloudsync`); the differences are E2E encryption and login-state sync. Connect app `CZL Browser` (`client_79372998`): data sync on, **E2E `required`** (cannot be turned off once data exists), collections `profiles` / `proxies` / `groups` / `states` (member) and `settings` (admin), history 0. Plans `personal` / `team` / `team-plus`, add-ons `seat` / `storage10`, all priced in Connect; capacity comes from `quotas.syncStorageGB`. Billing catalog 403 means billing is off and sync is free.

- **Spaces**: `local` (never uploaded; all pre-upgrade data), `me:<user id>`, `org:<org id>` (server ids `me` / org id). `browser_profiles` / `browser_proxies` / `browser_groups` carry `space` / `rev` (server seq) / `dirty` (outbound seq from `sync_counter`, 0 = clean) / `deleted` (tombstone). Bookmarks of synced spaces live in `space_settings` key `bookmarks`; `local` keeps `browser_bookmarks`. `space.State` is the current space; DAOs read/write the current space (profiles DAO lists all spaces; `Manager.List` filters, so running instances survive a switch). Writes mark dirty only when the synced fields (`*Wire` structs) change, so saving all profiles stays cheap. The builtin `__direct__` proxy is virtual in synced spaces. Same id never crosses spaces (`40904`); cross-space copy (`SyncCopyProfiles` / `SyncCopyProxies`) always mints new ids and copies referenced proxies. Read-only spaces reject writes (`40905`); team bookmarks are admin-only (`40911`). Startup migration and default seeding run in `local` before `initCloud` restores the last space.
- **Sync engine**: rows with `dirty > 0` are the SDK outbox (`cloudsync/adapter.go` + `syncstore`); DAO commits call `space.State.Edited` → `Engine.Save` to poke a push. Pulled rows land clean; local edits pending upload are not overwritten (409 → conflict). Conflicts always keep the server version and emit `sync:conflict` (no conflict copies: a copied profile would be a new fingerprint). Wire envelope `{"v":1,"data":...}`; newer versions are skipped and the cursor holds before them. After applying profiles, `Manager.ReloadProfiles` refreshes memory without touching runtime fields.
- **E2E**: all crypto and key lifecycle is `syncsdk.KeyManager` (namespace `czlbrowser/<user id>`), private keys in the DPAPI key store `data/sync/keys` (excluded from backups with the rest of `data/sync`). Flows: enroll → recovery code shown once (copy / save file + confirm; the modal is owned by `CloudOverlays` via `cloudStore.recoveryCode`, because enrolling flips keys to unlocked and unmounts the enroll panel); unlock by recovery code or approval from an unlocked device (6-digit SAS on both sides; unlocked devices poll pending requests every 30 s and pop `DeviceApprovalModal`); reset recovery code. Subscriptions start only when keys are unlocked, and every synced space is read-only on this machine until then (`accessOf` takes the key status; `ReadOnlyBanner`, the space switcher, the team page and copy-to all say whether to enable or to unlock; creating or joining a team while not enrolled prompts to enable). Team keys: owner/admin clients grant new members and rotate after removals during sync; ungranted members see `keyPending`. Keys stay on disk after logout so re-login needs no recovery code.
- **Login state**: when an instance in a writable synced space exits, `OnStopped` waits 3 s, packs the user data dir with `profilestate.Pack` (backup whitelist; the DPAPI `os_crypt` key is decrypted into the encrypted pack, `app_bound_encrypted_key` dropped on restore) into `data/sync/packs`, records it in `profile_states` and queues it. On push the pack is uploaded as 24 MB E2E blobs and the `states/<profile id>` doc is the manifest (parts, size, sha256, device). Before launch `PrepareLaunch` downloads and unpacks when the server rev is newer than `applied_rev` and nothing local is pending; the previous dir is kept as `.prev`. Running instances send presence on `profiles/<id>`. Presence is per device: each machine keeps a device id in `data/sync/device_id`, which is never backed up and is passed to syncsdk ≥ v1.9.0 with the device name. Starting an instance a teammate uses returns `40915`, and one your own other computer uses returns `40917`, and the UI offers `BrowserInstanceStartForce` (also after a failed download). Limit 512 MB per pack (`41302`). Packs are content the server cannot read, so after every successful sync the space owner or admin reports the blob ids still referenced by the space's `states` manifests (`blobrefs.go` → `PutBlobRefs`, syncsdk ≥ v1.10.0). Connect deletes unreferenced blobs and reduces usage 30 days later. The report is skipped while login states are pending upload or any `states` doc failed to apply, because an incomplete set would get live blobs deleted.
- **Teams & billing**: `app_org.go` / `app_billing.go` mirror TradeDocs. Leaving or closing a team requires its instances to be stopped, asks before dropping unpushed changes (`40910`) and deletes the local copy including user data dirs. Payment always happens on the Connect hosted checkout in the system browser; login uses a loopback callback with no custom protocol, so checkout URLs carry no `return`, and the purchase modal polls the entitlement fingerprint every 4 s for 15 min. Redeem codes (generated in Connect admin) are entered in 套餐与订阅 → 我的订阅 and go through `BillingRedeem` → `POST /api/oauth2/billing/redeem`. Connect caches entitlements for tens of seconds, so after a redeem the backend polls the fingerprint before refreshing. 我的订阅 has 管理订阅 (`BillingOpenManage` → Connect `profile/subscriptions`: renew, auto-renew, refunds) and lists each bought add-on with its next-period quantity (`pendingQuantity`). Owners/admins can lower that quantity in-app (`BillingSetAddOnQuantity` → `addon-quantity`, effective at renewal, raising it back to the current count reverts). The returned entitlement is written straight into the billing cache. Renewal always charges the plan plus the next-period add-on quantities.
- **Frontend**: the sidebar's account card (`shared/layout/AccountMenu.tsx`) shows plan, expiry and personal sync usage from `billing` / `sync`. `store/cloudStore.ts` holds sync / billing / presence state from `sync:*` and `billing:changed` events; `changeTick` makes list pages reload after a space switch or pulled changes. `/cloud` page has left nav (同步与加密 / 团队 / 套餐与订阅, `?tab=`). `ReadOnlyBanner` explains read-only spaces with purchase links. Errors arrive as `"<code> <phrase>"` and are shown via `errorText`.

## Key Conventions

- **Language**: All UI text, log messages, and comments are in Chinese
- **Go module**: `czl-browser` (not `czl-browser`)
- **CSS**: Tailwind CSS with CSS variables defined in the theme (no hardcoded Tailwind colors). CZL neutral palette: black/white/gray dominant; `--color-accent` is **near-black** (drives links/selection/active/icon coloring), brand blue `--color-brand` (`#2EA7E0`) only appears in the focus ring (`--color-ring`), progress bars and the Logo — never as link/button color. Nav current item and selected rows use `--color-brand-soft` bg + `--color-brand-strong` text; small option controls (pills, checkboxes) use the inverted near-black. Density is compact: controls h-8 (`sm` h-7), 13px body text, page title `text-base` with actions on the same row; list pages fill the height with an internally scrolling table and never add extra full-width strips (batch actions replace the group-pill row). Multi-category pages use `SectionPage` (left sub-nav + `?tab=`). No gradients in UI. Charts use `--color-chart-1`..`6`.
- **State management**: Zustand (lightweight stores in `src/store/`)
- **Icons**: Lucide React only (no emoji in UI)
- **Text selection**: `shared/appShell.ts` marks `html[data-app-shell]` only inside the Wails shell (a bare Vite page keeps browser defaults) and takes over Ctrl/⌘+A. Rules in `index.css` are wrapped in `:where()`: chrome is unselectable, `main`, dialogs, toasts, `pre`/`code`, inputs and `[data-selectable]` are selectable, and buttons/tabs/menu items/labels/Badge inside them stay unselectable. Ctrl/⌘+A selects only the last clicked `[data-select-block]`/`pre` (logs, backup log, recovery code) and selects nothing elsewhere; new content areas get `data-selectable`, never per-component CSS.
- **Frontend routing**: React Router v6, routes defined in `App.tsx`
- **Backend method naming**: `BrowserProfile*`, `BrowserProxy*`, `BrowserCore*` prefixes for Wails-bound methods
- **Type aliases**: `desktop/api_profiles.go` re-exports `browser.*` types (e.g., `type BrowserProfile = browser.Profile`) for Wails binding compatibility
